## Legacy knowledge lifecycle supplement

The publication boundary now applies to both enabled content creation and all edits/unpublishing of existing enabled content. An editor must explicitly save `enabled=false` drafts; omitting enabled retains the legacy true default and requires `knowledge.publish`. A publisher can publish, update verified facts, and disable them; an editor can resume draft editing only after authorized disabling. Direct negative API tests verify denied writes leave the stored record and guest retrieval answer unchanged, rather than relying on HTTP status alone. Cross-property writes also remain denied.

An inventoried call-site review found only two user-driven `save_knowledge` paths: the legacy API and Admin AI `faq.create`. Both explicitly supply the current principal's publication grant; the AI FAQ action always creates an unpublished draft. Other calls are synthetic tests/internal store use. A race regression commits a publisher change after the editor's ownership lookup but before its guarded conflict update; the editor receives a denial and the published fact remains intact. Initial race-fixture execution held its SQLite read cursor open and failed with a lock error; releasing the completed read corrected the fixture. The final run is **49 passed, 1 skipped, zero failed**, 5.72s; the skip is Linux RLIMIT_AS on macOS (already accepted separately inside the owned Linux lab container). [Evidence](evidence/security-2026-10-12.md).
